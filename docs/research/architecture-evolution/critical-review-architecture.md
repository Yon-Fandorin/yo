## Judgment

The prior design is directionally defensible, but retaining the engine must be an evaluated decision, not its opening axiom. Its largest execution gap is not a missing host crate: a native coding turn has a minimal base prompt, no automatic project-instruction assembly, no typed search, serial execution, and a binary approval policy whose process branch always asks. Rearranging these owners without changing that complete journey will preserve an inadequate agent.

Replace the serial turn/tool representation and UI-shaped startup result. Retain the semantic Runtime/Engine/Journal boundaries and provider/connector split because the inspected code gives them distinct responsibilities and valuable observable contracts. Introduce fewer new owners than the full target tree implies. A useful native coding turn, policy-backed process execution, and actual independent tool progress should precede large remote/Goal/MCP infrastructure claims.

The integrated README already acknowledges opaque shell conflicts and many failure cases; the criticism below is not that those warnings are absent. The problem is that several milestones can pass synthetic checks without delivering their headline product benefit.

## 1. Add a real native coding-agent prompt, with a product owner

**Evidence.** [backends/managed/src/backend.rs::NativeModelBackendConfig::default](../../../crates/backends/managed/src/backend.rs) supplies only `You are Yo, a careful software-engineering agent.`. CLI [execution/model/native.rs:175](../../../crates/yo-cli/src/execution/model/native.rs#L175) overrides argument allowance and execution-manifest digest, inheriting that prompt. `managed/backend/request.rs::start_model_round` inserts `self.contract.system_prompt()` as the System message. Pi `packages/coding-agent/src/core/system-prompt.ts::buildSystemPromptSections` explicitly assembles available tools, rules contributed by tools, project context, skills and cwd. Codex `core/src/session/session.rs` tracks custom/inherited/model base-instruction provenance and `session/turn.rs` obtains base instructions for requests.

**Impact.** Adding search, plans or permission controls without telling the native agent how to operate them can leave ordinary coding behavior weak even though every wire contract passes. A repo without AGENTS still needs an effective coding agent. The current A milestone covers instruction discovery but does not specify this missing product behavior.

**Decision: add / rework.** A pure private **product prompt assembler** should initially live alongside CLI execution preparation, taking admitted immutable context/tool capability values and returning versioned prompt bytes. CLI discovery owns filesystem/config I/O; the assembler owns product wording/tool-use guidance; managed request assembly owns count/send/replay. Move the product module with reusable host assembly only when extraction occurs. Do not put repository discovery or a mutable global settings bag in managed. No generic prompt framework is needed.

**Negative evidence.** Richer prose is not demonstrated quality improvement by itself. Existing tool descriptions and resolved skill snapshots already carry useful guidance. Preserve these; do not copy a large upstream prompt blindly. Pi's extension instructions and fallback behavior are not Yo requirements.

**Tests / acceptance.** Existing `connector_rounds.rs::resolved_skill_snapshot_is_counted_sent_and_retained_in_native_replay` is the count/send/replay precedent; `context_replay/idle_outcomes.rs::idle_nonreducing_summary_rejects_without_losing_original_context` protects no-loss behavior. Add consumer assertions for exact assembled bytes, no-tools mode advertising no unavailable actions, no unresolved skills presented as available, no duplicate delegated-host instruction injection, and old prompt/AGENTS remaining exact on historical resume. Run identical small coding tasks with and without AGENTS; evaluate task correctness and unnecessary approvals separately from prompt structure. Prompt revision/new-session selection may require `agent.backend.yo-managed-model-loop`, `agent.model.session-selection` and replay-contract owner deltas; do not silently revise saved contracts.

## 2. The grant design lacks its concrete process input bridge

**Evidence.** [execution/tools/registry.rs::run_command_definition](../../../crates/yo-cli/src/execution/tools/registry.rs) exposes one shell string and `ToolApprovalRequirement::Required`; file read/write/edit are Automatic. Configured command tools have fixed executable/argv artifacts and send validated dynamic arguments on stdin; accepted `agent.tool.local-execution-boundary` explicitly makes them Process/Required. [execution/tools/command.rs::CommandPlan](../../../crates/yo-cli/src/execution/tools/command.rs) has `Shell(String)` and `Prepared(...)` branches. The candidate grant policy says persistent rules apply to structured executable/argv/cwd/environment/sandbox, but does not select the model-visible path producing those admitted structured requests for ordinary cargo/git/test commands.

**Impact.** A grant repository and `/permissions` can be completed while routine commands still go through opaque shell and ask each time. This is a missing implementation bridge, not a missing warning.

**Decision: add and rework.** Select one concrete first automation surface: preferably a versioned `exec_process`-style structured tool with explicit executable, literal argv and workspace-relative cwd, host-owned environment and sandbox profile. Alternatively explicitly scope C to configured fixed command tools and provide useful shipped/user-configurable wrappers; admit that arbitrary shell remains per-call. Keep the old shell tool for compatibility and explicit broad actions. Host preparation resolves execution identity; permission policy derives exact authorization; sandbox applies the ceiling; scheduler receives host-derived claims. Do not infer a narrow scope from shell prefixes or model-declared readonly intent.

**Comparator / negative evidence.** Pi's beforeToolCall is a hook rather than confinement; Codex ToolOrchestrator combines policy requirements with sandbox execution. Neither proves safe shell parsing for Yo. A generic structured executable can still run an interpreter with broad effects: only enforced sandbox/explicit grants bound it. Existing unsandboxed explicit approval can remain honestly labeled.

**Tests / acceptance.** `managed/tests/approval_cleanup.rs::native_backend_required_approval_gates_tool_execution` demonstrates zero starts before approval and one after. Add an actual coding journey: run the same admitted test command twice under one chosen scope, change argv/cwd/executable/revocation generation and observe the correct reauthorization, reject unsupported confinement, then cancel/reap. Requires explicit new tool registry and approval-policy contract revisions; a CONTRIBUTING/workflow authorization change cannot alter runtime permission semantics.

## 3. Replace serial execution, but reject a misleading approval-HOL success criterion

**Evidence.** `managed/backend/tools.rs::advance_tool_queue` removes one `pending_calls.pop_first()`, installs `awaiting_approval`, and returns. [backend.rs::TurnState](../../../crates/backends/managed/src/backend.rs) has singular `active_tool/ready_tool/dispatch_tool/awaiting_approval`; `adapter/poll.rs` processes one branch and cannot schedule later calls while awaiting approval. This is direct code evidence of serialization, not a performance measurement. `tests/tool_execution.rs::native_backend_executes_multiple_tools_in_model_output_order` explicitly asserts serial starts and ordered replay.

**Current product reachability.** All built-in file tools are automatic. The shipping approval-required built-in is opaque `run_command`; configured commands are also opaque Process. Under the proposed exclusive claims, an approval-pending Process blocks later workspace reads by source-order conflict. The candidate's `read A / approval write B / independent read C` is therefore a synthetic scheduler fixture unless a newly scoped approval-required tool is actually shipped. README correctly warns about shell; implementation completion criteria must carry the same distinction.

**Decision: replace.** Implement an indexed ToolBatch state machine rather than adding parallel vectors to current flags. Call phase, cancellation, result ownership and retirement belong to one slot. First deliver independent readonly throughput; prioritize typed search and finding 2 for approval reduction. Avoid importing a general DAG, independent scheduler service or per-result acknowledgement protocol while the single worker's event-drain publication barrier suffices.

**Comparator / negative evidence.** Pi `agent-loop.ts::executeToolCallsParallel` awaits each `prepareToolCall` before starting Promise.all closures; a blocking hook can delay all launches. Codex `core/src/tools/parallel.rs` acquires its shared/exclusive gate before handler dispatch and drops it after the awaited handler, which can include approval. Both have parallel infrastructure without universal approval independence. Yo's proposed four-slot reorder window also intentionally stops later work when the oldest slot cannot retire; it is bounded concurrency, not elimination of every HOL wait.

**Acceptance.** Separate (a) deterministic reverse-read completion with ordered semantic publication and first-excess capacity tests, (b) a real shipping disjoint approval tool journey, and (c) opaque shell conflict remaining blocked. Include pending/ready/running mixed cancellation and failure after physical result before Journal publication. Keep current single-attempt, bounded output, source-order publication and exact approval invariants. Accepted managed/tool contracts already allow proven-independent concurrency, so enabling that subset need not reverse the core policy; new grant/claim meanings still require owner deltas.

## 4. Remove UI-shaped construction now; do not make GUI its justification

**Evidence.** [application/runtime/startup/model.rs::PreparedAgent](../../../crates/yo-cli/src/application/runtime/startup/model.rs) contains `TuiAgentConnection` and `yo_tui::RestoredPromptHistory`. `runtime/print.rs::run_print_session` creates `LiveOptions` with Inline/Rich/theme values, then unwraps the prepared TUI connection back into AgentSession. [state/config.rs](../../../crates/yo-cli/src/state/config.rs) combines command/skill configuration and Theme/PromptTemplates/output/clipboard state. The neutral consumer already exists: print.

**Decision: replace / remove.** Replace that shared preparation result with a neutral Session/runtime preparation value and frontend-specific extras. Remove TUI options from the execution factory's signature. A TUI adapter is constructed by terminal startup after preparation; print consumes Session directly. Keep process termination policy in executable. Split immutable execution configuration from presentation configuration without a new global service locator. A new host crate is a later packaging choice; this refactor does not need remote protocol, controller leases or GUI.

**Comparator / negative evidence.** Pi separates cwd-bound services from session construction, but its runtime replacement disposes the previous runtime before creation; preserve Yo's candidate failure behavior rather than copying that ordering. Codex's explicit consuming shutdown is useful; mandatory JSON transport and its queue policies are not prerequisites for local Yo construction.

**Acceptance / owners.** Compare existing print/start/resume/approval/interrupt/shutdown consumers, partial-preparation cleanup and failure retaining the old active session. Existing core [agent_session/tests/flow.rs::retains_session_start_and_cleanup_failures](../../../crates/yo-core/src/agent_session/tests/flow.rs) is a relevant lifecycle check. Move assembly ownership out of CLI only with a separate explicit delta to `agent.core.frontend-independent-boundary` and `agent.backend.execution-topology`; a neutral private CLI module is smaller and useful immediately.

## 5. Replace shared-lock execution with staged owner transitions before adding waits

**Evidence.** [yo-core/src/agent_session/worker/events.rs::poll](../../../crates/yo-core/src/agent_session/worker/events.rs) acquires shared SessionState and holds it during `runtime.poll_event()`. `worker/commands.rs::execute` holds the same guard during runtime command execution. [agent_session/admission.rs](../../../crates/yo-core/src/agent_session/admission.rs) uses this state to decide exact current-turn/request admission. Managed poll can finalize checkpoints, count/prepare a new model request, perform semantic output handling and executor shutdown; it is not merely reading a ready flag.

**Impact.** Future budget permits, memory guards, host claim waits and child joins inserted here can block admission or create lock cycles. This source does not prove a present production deadlock; it does show the present lock scope is not safe as a generic async-extension boundary.

**Decision: rework.** Keep one semantic worker owner. Stage external preparation/wait results outside the shared admission mutex and revalidate turn/generation before commit. Replace the unstructured set of TurnState optional phase fields with private execution/compaction/tool states, instead of preserving the bag and adding six more bags. A full actor framework and wholesale Runtime/Engine merger are not justified.

**Comparator / negative evidence.** Pi async loop and Codex Arc<Session>/services are not permission to expose a large mutable host bag. Exact admission races currently prevented by the lock must still be prevented after reducing its scope. Moving the unlock without an epoch check is incorrect.

**Tests / acceptance.** Existing [agent_session/tests/flow.rs::rejects_an_exact_steer_after_its_observed_turn_finishes](../../../crates/yo-core/src/agent_session/tests/flow.rs), `prevents_binding_replacement_from_overtaking_idle_compaction`, plus bounded admission/backpressure behavior are preservation cases. Add stalled host-preparation/permit fixtures proving exact interrupt/admission responsiveness and stale completion rejection. This is a prerequisite to new waits in D/F, not an excuse for a blanket engine rewrite.

## 6. Merge dispatch mechanics, not request semantics, before claiming a hard Goal budget

**Evidence.** `managed/backend/request.rs`, `compaction/active.rs`, `compaction/idle.rs` and `secret.rs` each directly invoke `connector.start`. Ordinary `start_model_round` checks `maximum_model_rounds`; protected and summary dispatch have separate lifecycle paths. `ModelRequestAccepted` is observed after dispatch and cannot serve as a permit. The candidate recognizes this; it must be an implementation gate, not an optional cleanup.

**Decision: merge / retain.** One private prepared-request dispatch gate should consume immutable request/accounting plus an applicable authorization/permit, then produce the one stream owner. Preserve different preconditions and receipt barriers for ordinary, summary and terminal-secret paths. Prefer synchronous worker-owned reservation when possible; if another owner must answer, use staged bounded commands/outcomes outside finding 5's guard. Do not create a new generalized billing service.

**Comparator / negative evidence.** Pi's request transform and Codex base-instruction request assembly demonstrate where shared request construction lives; neither is evidence of Yo's desired hard budget. Current Yo context accounting, replay and absent cache usage semantics are strengths to retain. Token count quality may be advisory for some profiles; a hard logical-request cap must not be labeled hard dollar/token spend.

**Acceptance.** One first-excess test for each dispatch kind; reservation survives uncertain delivery, no automatic refund/retry after effect ambiguity, secret receipt failure never resends. Preserve `idle_nonreducing_summary_rejects_without_losing_original_context`, `serializes_only_the_declared_responses_request_capabilities`, `cache_read_usage_distinguishes_omission_from_reported_zero`. Goal accounting adds managed-loop/Journal semantics; unsupported delegated inner rounds must remain unsupported for this hard guarantee.

## 7. Decouple useful native plans from the full Goal/budget/child subsystem

**Evidence.** Yo already has [yo-core/src/event/plan.rs::ActivityPlan](../../../crates/yo-core/src/event/plan.rs) with bounded snapshot encoding, but it is host-observed presentation state, not a native plan mutation tool or authoritative Goal. Native registry has no plan tool. The candidate bundles typed Goal/Plan and hard-budget plumbing under F1, then child sessions under F2. Codex has a dedicated Goal API/runtime and spawn guard; these demonstrate substantial distinct mechanisms. Pi's simpler core is counterevidence that every useful plan needs a Goal ledger.

**Impact.** The native agent can remain unable to show and update a structured working plan while waiting for parent-funded request reservations and crash-join machinery. Conversely, calling existing ActivityPlan a full implemented native plan would be false.

**Decision: split / reuse.** Introduce a small native plan-update capability with one explicit plan owner and reuse ActivityPlan solely as its frontend projection. Keep goal objective/acceptance evidence and enforced budget as separate capabilities. F1a can ship a bounded plan state preserved through context/continuation; F1b implements hard limits; F2 adds children with their chosen funding contract. Do not make plan step completion prove tests passed or Goal success. Do not weaken funded child accounting to accelerate plan UI.

**Acceptance / dependencies.** Native model creates/revises plan, user observes it, compaction preserves current authoritative plan, malformed/stale update is rejected, and a host-reported completed step cannot complete the Goal. Existing ActivityPlan bounds are an encoding precedent, not sufficient behavioral tests. New plan mutation/continuation meaning needs runtime/Journal contract decisions. Child work remains dependent on its actual budget/ownership contract; Codex `PendingSpawn` cleanup pattern is useful but not a replacement for Yo crash join.

## 8. Make first MCP usefulness a compatibility gate, not only a safe fixture

**Evidence.** Yo [tool/schema.rs::validate_schema_node](../../../crates/yo-core/src/tool/schema.rs) rejects every keyword outside a small closed set and requires a single string type for every node; `tests/schema.rs::registry_rejects_malformed_closed_subset_schemas` codifies rejection. The proposed first MCP profile additionally requires text-only results, readonly lifetime workspace access, isolated state and limited external effects. Pi `coding-agent/src/extensions/mcp/runtime.ts` actually supplies stdio/HTTP/OAuth connections and resource/tool clients; Codex MCP handlers retain tool specs, schema limits and supported parallel flags. Neither reference's breadth is reached by simply completing a Yo initialize/tools/list fixture.

**Decision: add a concrete compatibility witness; avoid premature framework.** Pick at least one named useful real server/tool inventory for the first coding journey and record which exact schemas/content/effects pass. Run its actual add/connect/discover/call/cancel/reconnect/remove path when implementation is authorized. If none fit, either choose a justified versioned wider schema/content profile or label the initial result a restricted experimental adapter. Do not silently delete `$ref`/unions/defaults or stringify unsupported content. Connection manager owns lifecycle; core owns admitted schema/semantic values; sandbox owns process ceiling. Keep codemode deferred until nested dispatch/accounting really needs it.

**Negative evidence.** This review does not establish that every real server fails the closed profile; no inventory corpus or live server was run. The gap is missing useful compatibility evidence, not permission to weaken confinement or copy all upstream extension machinery. First-party tests for exact bounds and startup cleanup remain necessary.

**Acceptance / contracts.** Demonstrate a genuine useful server with captured schema/result fixtures; state all rejected capabilities before launch and preserve ordinary local tool operation when discovery fails. Any widened schema dialect/new execution-host profile requires `agent.tool.local-execution-boundary` and managed binding/replay deltas. Retain old registry bytes and exact resume.

## Priority and hard boundaries

1. Ship an effective new-session prompt + selected project instructions + typed search + current UI fixes. These change actual coding success without remote infrastructure.
2. Remove TUI-shaped preparation and implement the concrete structured process/grant path. Continue honoring mandatory runtime/OS approvals; reduce unnecessary repeated prompts by new admitted policy, not by bypassing gates.
3. Replace serial ToolBatch and measure readonly throughput separately from approval savings. Existing opaque command conflicts remain ordered. Add staged worker waits/unified dispatch before new budget/service waits.
4. Deliver native plan state independently; then the explicitly selected hard Goal/child model. Validate first MCP against a real useful profile rather than counting an interface as parity.

No accepted SOT was changed. Proposed owner/behavior deltas above must go through the repository-selected authority workflow if implemented. Existing exact-call approval, one execution attempt, source-order semantic publication, secret exclusion and exact historical replay remain required throughout. Static review is not OS isolation, provider entitlement, latency, race, paid-model quality or end-user parity evidence.

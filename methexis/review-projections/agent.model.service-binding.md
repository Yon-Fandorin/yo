Action이 `preserve`이면 expected credential과 planned exact public에서 credential mutation 없이 완료합니다. Expected credential과 expected public이면 어느 disconnect intent든 abandon하고, planned credential과 expected public 및 나열하지 않은 상태는 conflict입니다. Journal phase는 저장소 상태보다 뒤처질 수 있고 exact table 비교 후에만 전진할 수 있습니다. 저장소에 없는 commit을 phase가 주장하면 abandon이 아니라 conflict입니다. 복구는 임의 revision 변경에서 ownership을 추론하거나 secret을 복원하거나 revision을 발명하거나 관련 없는 상태를 덮어쓰지 않습니다. Exact retry는 idempotent합니다.

ConnectionRepository 경로가 없으면 revision token `absent`와 binding 및 preference가 없는 표준 빈 managed snapshot입니다. 최초 writer는 같은 directory에 현재 사용자 소유이고 no-follow이며 mode `0600`인 임시 파일을 배타적으로 만들고 prepared snapshot을 durable하게 기록한 뒤 expected repository revision이 계속 absent일 때만 atomically rename합니다. Concurrent winner가 있으면 다시 읽어 exact intent reuse 또는 conflict로 처리합니다. 기존 write는 bounded regular snapshot, prepared opaque revision CAS, durable atomic replace, old-or-new recovery, unrelated preservation을 사용합니다. 주입된 repository도 같은 의미를 제공해야 합니다.

OpenRouter, QwenCloud, Kimi는 configured Provider로 유지합니다. Base profile은 manual model entry의 반복을 줄일 수 있고 model override는 예외적인 값을 해당 model 옆에 둘 수 있습니다. 저장된 snapshot은 이 값을 명시적이고 읽기 쉽게 유지하며 custom profile은 advanced path로 둡니다. OpenRouter와 Kimi는 각각 여기에 설명한 서로 다른 인증된 account-model inventory protocol을 소유합니다. 어느 protocol도 일반적인 Model Connector 책임이 되지 않고 다른 Provider의 wire field를 decode하면 안 됩니다.

OpenRouter Provider·Account binding은 정확한 OpenRouter ProviderId, normalized endpoint 하나, 완전한 base profile을 제공할 때만 model entry를 생략할 수 있습니다. 이 binding은 routable ModelTarget이 아니라 discovery seed입니다. Interactive 두 부분 target admission은 닫혀 있습니다. `yo connect Provider:Account`는 정확히 설정된 OpenRouter discovery seed, QwenCloud catalog seed, Kimi catalog seed만 허용하고 다른 모든 두 부분 target을 거절합니다. 이 문단의 인증된 remote discovery는 OpenRouter seed만 수행하며 QwenCloud와 Kimi는 아래의 별도 catalog flow를 따릅니다. OpenRouter command는 기존 path prefix를 바꾸지 않고 normalized endpoint에 `models`, `user` path segment를 덧붙여 인증된 same-origin `GET`을 한 번 수행합니다. In-memory CandidateSecret은 Bearer credential로만 보내고 origin이 바뀐 곳에는 전달하지 않습니다. Same-origin redirect는 최대 3회, 연결 timeout은 10초, response-header timeout은 각 dispatch attempt마다 새로 시작하는 30초, response-body inactivity timeout은 비어 있지 않은 chunk마다 reset되는 30초, absolute deadline은 2분입니다. 성공 response는 JSON media type이고 8,388,608 byte 이하여야 합니다. `data` array는 4,096 row 이하여야 하며 4,097개 이상이면 일부를 자르거나 고르지 않고 row admission 전에 response 전체를 거절합니다. Transport, status, media-type, size, decode 진단은 credential과 response-body 내용을 노출하지 않습니다. 이 범위에는 background refresh, disk cache, automatic retry가 없습니다.

Discovery response에는 `data` array가 필요합니다. Inventory membership과 현재 runtime availability는 분리합니다. Object가 아니거나 string `id`가 없는 row는 표현 가능한 identity가 없으므로 생략합니다. `canonical_slug`가 아니라 `id`를 durable ModelId로 사용하며 유효하지 않은 ModelId도 생략합니다. Identity 검증 뒤에는 disabled row이더라도 exact ModelId의 첫 row가 이기고 모든 duplicate를 무시합니다. Capability, limit, profile의 다른 조건은 그 row를 in-memory inventory에서 제거하지 않습니다. `architecture.input_modalities`, `architecture.output_modalities`, `supported_parameters`는 capability evidence입니다. 각 값은 string만 담은 array여야 합니다. 유효한 array는 duplicate가 없고 순서와 무관한 set으로 해석하며, 알 수 없는 string은 bounded untrusted in-memory metadata로 유지합니다. Capability evidence가 없거나 malformed이면 row를 숨기지 않고 `capabilities unavailable`로 disabled 처리합니다.

최초 runtime capability set은 input과 output capability set이 모두 `text`를 포함할 때 request를 허용합니다. Enabled row는 Yo의 text input·text output boundary로만 호출하므로 `text`와 함께 다른 modality를 광고해도 model을 disabled 처리하지 않습니다. 유효한 row에 text input이 없으면 `text input unsupported`, text input은 있지만 text output이 없으면 `text output unsupported`로 disabled 처리합니다. `tools` 또는 `tool_choice`가 없어도 text model을 disabled 처리하지 않습니다. 이 경우 effective tool policy는 위 configured-policy intersection에 따라 `no-tools/v1`이 됩니다. Configured tool policy가 최초에 지원하는 두 값 밖이면 `tool policy unsupported`로 disabled 처리합니다. Optional `reasoning` parameter는 표시 badge에만 영향을 주고 reasoning parameter를 발명하지 않습니다. Availability와 reason은 ModelId나 durable provider identity의 일부가 아닌 파생 runtime fact입니다. 이후 reviewed runtime modality 또는 policy 지원이 확장되면 provider-specific allowlist나 connection migration 없이 같은 exact ModelId를 다시 평가합니다.

Optional remote limit가 없거나 JSON null이면 configured limit 값을 유지합니다. `context_length` 또는 `top_provider.max_completion_tokens`가 있는데 양의 정수가 아니면 row를 숨기지 않고 disabled 처리하며, null이 아닌 `top_provider`가 object가 아닌 경우도 같습니다. 같은 configured binding에 이미 선언된 model이면 authored whole-field override가 우선합니다. 그 밖에는 remote `context_length`가 base `input_token_limit`를, remote `top_provider.max_completion_tokens`가 base `max_output_tokens`를 값이 있을 때 교체합니다. Endpoint, dialect, tokenizer, structured parameter, verification profile은 명시적으로 설정한 base 값을 유지하고 tool policy는 위 capability intersection을 따릅니다. 결과 complete profile이 유효하지 않으면 `profile unavailable`로 disabled 처리합니다. 여러 조건이 동시에 실패하면 concise primary reason은 capability evidence unavailable, text input unsupported, text output unsupported, tool policy unsupported, profile unavailable 순서를 사용합니다. 정규화한 in-memory inventory는 case-fold한 display label과 exact ModelId 순으로 정렬하며 enabled selection은 두 번째 fetch나 추정 metadata 없이 그 정확한 normalized row를 보존합니다.

Remote에서 온 모든 string은 신뢰할 수 없는 terminal data입니다. Picker와 이후 preview는 이를 raw로 쓰지 않습니다. ASCII U+0020~U+007E 밖의 byte 및 ASCII quote와 backslash byte를 되돌릴 수 있는 visible escape로 표시하므로 C0/C1 control, ESC/OSC payload, line separator, bidi control, non-ASCII byte가 terminal state에 영향을 줄 수 없습니다. Remote `name`은 trim한 UTF-8 값이 비어 있지 않고 96 byte 이하일 때만 사용하며, 그렇지 않으면 escaped ModelId를 display로 사용합니다. Picker result는 각각 terminal row 하나만 차지하고 측정한 terminal width에 맞춰 visible ellipsis로 줄입니다. Selected detail과 이후 preview는 완전한 escaped ModelId를 빠짐없이 wrap합니다. Search는 원래 ModelId와 허용된 원래 display name을 비교하지만 query 표시는 같은 safe boundary를 사용합니다. 이 규칙은 표시에만 영향을 주며 exact unescaped ModelId가 request와 durable identity로 유지됩니다.

정규화한 inventory에 유효한 ModelId가 하나도 없으면 picker terminal mode에 들어가기 전에 discovery가 실패합니다. 그렇지 않으면 모든 row가 현재 disabled여도 controlling-TTY picker를 열고 Provider와 Account를 한 번만 보여주며 display name과 ModelId에 대한 local case-insensitive substring search를 지원합니다. 모든 matching inventory item은 visible result row가 최대 8개인 viewport를 통해 접근할 수 있습니다. 처음에는 첫 match에 focus를 둡니다. Up·Down은 result 하나씩 focus를 이동하고 처음과 마지막 result에서 wrap하지 않고 멈추며 viewport는 focus item이 보이는 데 필요한 만큼만 scroll합니다. Search query를 수정할 때마다 전체 match set을 다시 계산하고 첫 result에 focus를 둡니다. Query에 맞는 result가 없으면 focus 없이 picker를 계속 열어 두어 query를 수정할 수 있고 이때 Enter는 아무 동작도 하지 않습니다. Enabled row에서 Enter를 누르면 선택합니다. Disabled row에서 Enter를 누르면 picker를 유지하고 concise availability reason을 보여줍니다. Escape 또는 interrupt는 취소합니다. 각 row는 Model과 간결한 context, output, tool, reasoning, availability 정보를 식별하며 Provider, Account, complete profile을 반복하지 않습니다. 최초 terminal-mode mutation부터 scope-owned cleanup boundary 하나가 selection, Escape, interrupt, render·input failure, panic unwind, ordinary error를 포함한 모든 exit에서 이전 terminal mode를 복원하고 dynamic panel을 제거합니다. Cleanup 뒤에만 선택한 exact ModelTarget을 기존의 간결한 connection preview로 넘깁니다. `--verbose`일 때만 이후 preview가 complete resolved profile을 펼칩니다. Confirmation 전 취소하거나 disabled row를 살펴본 경우 CandidateSecret을 버리고 새 journal, credential mutation, public mutation을 만들지 않습니다.

외부 서비스용 interactive `yo connect`는 계속 binding 하나만 정확히 바꿉니다. Exact ModelTarget은 기존 configured-model 경로를 따릅니다. OpenRouter 두 부분 discovery target은 operation lock을 얻고 pending recovery를 해결하고 ConfigSnapshot과 repository state를 캡처하고 exact configured discovery seed를 해석한 뒤 CandidateSecret 하나를 읽어 account-scoped inventory 하나를 가져오고 operator가 enabled Model 하나를 정확히 고르게 한 다음 같은 exact connect plan을 준비합니다. Disabled item은 선택할 수 없고 plan, journal, credential mutation, public mutation을 만들 수 없습니다. Discovery는 모든 model이나 profile default를 추론하지 않습니다. 같은 Provider·Account pair는 secret을 교체하거나 추가합니다. 이후 preview는 exact binding union과 사용량을 공개하고 한 번 확인하며 verification은 retry하지 않습니다. Discovery에 쓴 같은 CandidateSecret을 필요한 모든 retained·prospective complete binding에 대해 검증합니다. 마지막 ConfigSnapshot 검증, secret-free journal 게시, credential-first commit, public commit, recovery 의미는 바뀌지 않습니다. 선택한 `no-tools/v1` binding은 같은 bounded no-tool path로 검증하고 이후 빈 tool registry로 실행하며 `local-tools/v1` 동작은 그대로 유지합니다. 성공은 authentication, exact entitlement, endpoint와 dialect 수용, 유한한 경계의 semantic terminal result를 증명하며 실패 종류는 구분합니다. Session-selection 계약이 first-success preference transition을 제공하고 같은 public CAS가 binding과 함께 게시합니다.

설정된 binding은 endpoint, base profile, model entry를 authoring하는 대신 built-in catalog adapter profile 하나를 선택할 수 있습니다. `catalog`는 정확한 `yo.versioned-profile-id/v1` 문법을 사용하고 닫힌 in-process registry 하나를 통해 해석합니다. 각 adapter는 정확한 ProviderId, provider display fallback, normalized endpoint, inventory mode, admitted row 하나를 complete binding으로 만드는 데 필요한 typed profile data를 atomically 소유합니다. Release-owned static adapter는 bounded model membership과 닫힌 whole-field per-model replacement도 소유합니다. Authenticated dynamic adapter는 정확한 inventory request·decoder와 닫힌 release-owned behavior overlay를 소유하며, remote membership이나 metadata는 decoder에 명시적으로 할당된 field만 채울 수 있고 실행 동작을 발명할 수 없습니다. Binding은 계속 AccountId 하나를 authoring하며 account 또는 provider display label을 authoring할 수 있지만, `catalog`가 있으면 `base_url`, `profile`, `models`는 없어야 합니다. Provider mismatch, 알 수 없는 catalog profile, 유효하지 않은 adapter row·overlay, adapter가 정의한 duplicate rule 뒤의 중복 ModelId, catalog와 manual 연결 field의 동시 사용은 설정 실패입니다. `catalog`가 없으면 기존 explicit endpoint, base-profile, model-entry 규칙은 바뀌지 않습니다.

Static catalog registry는 정확히 `qwencloud-coding-plan-cn/v1`, `qwencloud-coding-plan-intl/v1`, `qwencloud-token-plan-team-intl/v1`만 허용하며 모두 ProviderId `qwencloud`에 결합됩니다. 각각 normalized endpoint `https://coding.dashscope.aliyuncs.com/v1/`, `https://coding-intl.dashscope.aliyuncs.com/v1/`, `https://token-plan.ap-southeast-1.maas.aliyuncs.com/compatible-mode/v1/`을 소유합니다. 완전한 base profile과 per-model replacement는 해당 공식 plan 문서에서 도출한 repository-owned typed data입니다. General pay-as-you-go, workspace-dedicated 또는 그 밖의 QwenCloud endpoint는 URL에서 catalog를 추론하지 않고 explicit manual binding으로 유지합니다. 이후 static Provider나 plan을 추가하려면 generic discovery라고 주장하지 않고 검토된 closed-registry 확장이 필요합니다.

Catalog profile은 안정적인 adapter 동작과 service 또는 plan family를 명명하며 content-addressed inventory snapshot이나 entitlement set을 나타내지 않습니다. 각 release-owned static catalog는 고유 row가 4,096개 이하인 결정적이고 network-independent인 table 하나를 가집니다. Authenticated dynamic catalog는 bounded invocation-local snapshot 하나만 보유하고 이를 persist, refresh하거나 durable state로 취급하지 않습니다. 같은 catalog profile 아래 static table이나 dynamic behavior overlay를 갱신하려면 공식 provider-source evidence와 일반 review가 필요하지만 설정이나 durable state를 바꾸지는 않습니다. 제거·부재·변경된 candidate는 이미 저장된 complete managed binding을 삭제하거나 다시 쓰지 않습니다. Startup은 정확한 durable field를 decode하고 이제 지원되지 않는 binding은 routable하지 않은 quarantined 상태로 분류합니다. 이후 table, snapshot, overlay에서 같은 좌표를 선택했을 때 field가 다르면 implicit migration이 아니라 명시적인 replacement epoch가 됩니다. Binary 또는 catalog가 갱신되어도 operation journal의 exact planned public byte가 recovery authority로 유지됩니다. Recovery는 현재 release가 새 addition으로는 거절할 기존 valid journal plan도 완료한 뒤 recovered binding을 decodable·removable하지만 selectable·verifiable·routable하지 않은 상태로 격리합니다.

Catalog membership은 model이 현재 release-owned table 또는 invocation-local authenticated snapshot의 candidate라는 뜻일 뿐입니다. Account 또는 CandidateSecret에 그 model 사용 권한이 있다는 증거로 표시해서는 안 됩니다. Static row, dynamic metadata, release-owned overlay는 routable complete binding을 만들기 전에 explicit typed text modality, tool support, reasoning presentation evidence, limit, dialect, tokenizer, structured parameter, tool policy, verification profile을 함께 제공해야 합니다. Runtime capability를 지원하지 않거나 complete overlay가 없는 row는 concise reason과 함께 보이지만 disabled 상태로 유지하고 provider-specific allowlist로 유효한 dynamic ModelId를 숨기지 않습니다. Catalog string은 같은 terminal-safe presentation boundary를 통과하며 picker는 기존 search, viewport, cancellation, disabled-selection, cleanup 동작을 유지합니다. Reasoning label은 remote metadata와 effective execution mode를 구분합니다. 검토된 release-owned overlay는 optional remote metadata가 빠졌을 때 더 강한 exact-model fact를 제공할 수 있지만 명시적으로 모순되는 remote 값은 row를 `capability conflict`로 disabled 처리합니다. 이런 overlay가 없으면 missing·malformed metadata는 unknown이며 동작을 넓힐 수 없습니다.

Catalog binding은 onboarding seed이며 bundled row 전체를 manual ModelCatalog로 확장하거나 startup에서 routable하게 만들지 않습니다. Interactive `yo connect qwencloud:Account`는 정확히 설정된 QwenCloud catalog seed 하나에만 허용합니다. Operation lock 아래에서 command는 pending recovery를 해결하고 ConfigSnapshot과 repository를 캡처한 다음 credential이나 network request 없이 고정된 in-process catalog를 해석하고 operator가 enabled row 하나를 선택하게 합니다. 취소하거나 disabled row를 살펴보는 일은 credential input 전에 일어나며 journal, credential mutation, public mutation을 만들지 않습니다. 설정된 catalog의 row를 가리키는 exact `qwencloud:Account:Model`은 기존 paired `--credential-file PATH --yes` non-interactive path를 포함하여 picker를 건너뛸 수 있습니다. 해당 catalog에 없는 ModelId는 explicit manual binding이 필요합니다.

Catalog row 하나를 선택한 뒤 command는 CandidateSecret 하나만 읽고 일반적인 one-binding connect plan과 concise preview를 준비하며 interactive일 때 한 번 확인한 다음 기존 candidate-only complete binding-union verification을 수행합니다. Verification은 새 intent나 repository mutation 전에 선택한 exact ModelId, entitlement, endpoint, dialect, resolved profile, semantic terminal result를 증명합니다. Verification 거절을 catalog unavailability로 바꾸지 않고 secret이나 response body를 노출하지 않으며 새 operation은 commit되지 않은 상태로 남습니다. 마지막 ConfigSnapshot 검증, secret-free journal 게시, credential-first commit, public commit, recovery, first-success preference, safe diagnostic은 explicit external ModelTarget connect와 동일하게 유지합니다. QwenCloud onboarding은 model-list request, 문서 scraping, Alibaba management API call, background refresh, disk catalog cache, probing, fallback, automatic retry를 수행하지 않습니다.

Dynamic catalog registry는 ProviderId `kimi`, provider display fallback `Kimi`, normalized endpoint `https://api.moonshot.ai/v1/`에 결합된 정확한 `kimi-platform-ai/v1`도 허용합니다. 이 profile은 `.ai` Kimi Platform service만 뜻합니다. `.com` credential과 교환할 수 없고 URL을 검사해 다른 platform profile을 추론하지 않습니다. Interactive `yo connect kimi:Account`는 operation lane과 pending recovery를 해결하고 ConfigSnapshot과 repository를 캡처하고 CandidateSecret 하나를 읽은 뒤 단일 path segment `models`를 붙여 Bearer-authenticated same-origin `GET`을 한 번 수행합니다. Same-origin redirect는 최대 3회이고 OpenRouter와 같은 10초 connect, attempt별 30초 response-header, non-empty body마다 reset되는 30초 inactivity, 2분 absolute inventory deadline을 사용합니다. JSON media type을 요구하고 body를 8,388,608 byte로 제한합니다. `data` array가 4,097 row 이상이면 row admission 전에 snapshot 전체를 거절하며 자르거나 일부를 선택하거나 picker를 열지 않습니다. Credential과 response body를 diagnostic에 노출하지 않고 retry, background refresh, disk cache, documentation scraping을 하지 않습니다.

Kimi response는 정확한 top-level `object: "list"`와 `data` array를 가져야 합니다. Object가 아닌 row, `object`가 정확한 `"model"`이 아닌 row, string `id`가 없는 row, invalid ModelId는 사용할 model identity가 없으므로 생략합니다. Row는 normalized ModelId search key와 exact ModelId 순서로 정렬합니다.

최초 Kimi behavior overlay는 정확한 `kimi-k3`를 recommended flagship row로 만들고 정확한 `kimi-k2.6`을 available non-thinking fallback으로 유지합니다. K3 complete profile은 remote의 positive `context_length`가 131,072보다 크고 검토된 ceiling 1,048,576 이하일 때만 사용하고, release-owned `max_output_tokens` 131,072, `utf8-bytes/v1`, `kimi-chat-completions`, 정확한 `reasoning_parameters` `{ "effort": "max" }`, 빈 `optional_request_parameters`, `local-tools/v1`, `semantic-terminal/v1`, `kimi-private-local-plaintext/v1`을 사용합니다. K3는 overlay가 정한 text-in/text-out·reasoning-required 모델입니다. `supports_reasoning`이 missing이어도 그 검토된 사실을 약화하지 않지만 explicit false이면 `capability conflict`로 disabled 처리합니다. Picker badge는 `reasoning required/max`와 `recommended`이며 `off`가 아닙니다. K2.6 profile은 remote의 positive `context_length`가 32,768보다 크고 262,144 이하일 때만 사용하고, release-owned `max_output_tokens` 32,768, `utf8-bytes/v1`, `kimi-chat-completions`, 빈 `reasoning_parameters`, 정확한 `optional_request_parameters` `{ "thinking": { "type": "disabled" } }`, `local-tools/v1`, `semantic-terminal/v1`, `semantic-only/v1`을 사용합니다. Reasoning badge는 true·false·unknown에 따라 `available/off`, `unavailable/off`, `unknown/off`를 유지합니다. Remote context가 모델의 닫힌 범위를 벗어나면 `profile unavailable`입니다. 정확한 `kimi-k2.5`는 `provider retirement`, K2.7 Code와 forced-thinking K2 row 및 현재·미래의 다른 ModelId는 distinct request·replay profile이 검토될 때까지 보이지만 `profile unavailable`로 disabled 상태입니다. Prefix, substring, remote capability flag만으로 unknown future ModelId를 enabled로 바꾸지 않습니다.

`kimi-chat-completions`를 명명하는 새 complete binding의 admission은 manual·managed provenance와 무관하게 닫혀 있습니다. 두 허용 variant 모두 exact ProviderId `kimi`, normalized endpoint `https://api.moonshot.ai/v1/`, `utf8-bytes/v1`, `local-tools/v1` 또는 안전하게 좁힌 `no-tools/v1`, `semantic-terminal/v1`을 요구합니다. K3는 추가로 exact ModelId `kimi-k3`, `131,072 < input_token_limit <= 1,048,576`, exact `max_output_tokens` 131,072, exact reasoning effort `low`·`high`·`max` 중 하나, 빈 `optional_request_parameters`, exact replay profile `kimi-private-local-plaintext/v1`을 요구하며 catalog는 `max`를 만듭니다. K2.6은 exact ModelId `kimi-k2.6`, `32,768 < input_token_limit <= 262,144`, exact `max_output_tokens` 32,768, 빈 `reasoning_parameters`, exact thinking-disabled `optional_request_parameters`, exact replay profile `semantic-only/v1`을 요구합니다. 차이가 있으면 add·replacement의 connection verification, 일반 model transport, 새 intent 게시 전에 typed unsupported-binding 또는 private-replay-consent-required failure가 됩니다. Kimi Connector는 transport 전에 선택된 variant의 complete envelope를 방어적으로 다시 검사합니다. Mandatory recovery는 new admission이 아닙니다. Re-verification이나 current-overlay reinterpretation 없이 기존 valid journal의 exact public byte를 완료한 뒤 unsupported recovered binding을 quarantine합니다. 이미 저장되었거나 복구된 unsupported binding은 startup conflict report와 journal recovery를 위해 decode할 수 있고 `yo disconnect`로 제거할 수 있지만 selectable·verifiable·routable하지 않습니다. Manual-only binding은 `config.yaml`을 편집해 제거할 수 있습니다. Admission 때문에 stale state를 삭제할 수 없게 만들거나 cross-version journal을 고립시키면 안 됩니다. 이후 ModelId, endpoint, request mode, limit ceiling, replay profile, profile expansion에는 manual-config bypass가 아니라 reviewed contract revision이 필요합니다.

Enabled Kimi row를 선택하면 두 번째 fetch 없이 그 exact normalized row와 CandidateSecret을 유지합니다. 취소하거나 disabled row를 살펴보면 in-memory secret을 버리고 새 plan, journal, credential mutation, public mutation을 만들지 않습니다. 그 뒤 일반적인 one-binding preview와 candidate-only binding-union verification으로 들어가며 verification은 disabled request-local tool exposure와 선택된 exact K3 또는 K2.6 request profile을 사용합니다. K3 verification은 Session replay를 만들지 않고 private assistant state를 검증한 뒤 버립니다. K3 preview는 일반 Session이 정확한 tool-loop·resume fidelity를 위해 bounded provider-private assistant state를 current-user-only local Session repository에 암호화하지 않고 보존한다는 사실을 알립니다. `--yes` 또는 interactive confirmation은 captured plan의 exact versioned storage fact를 승인하고, 그 뒤에만 managed binding이 `kimi-private-local-plaintext/v1`을 게시할 수 있습니다. 필요한 retained·prospective binding 모두가 semantic terminal에 성공해야 마지막 ConfigSnapshot guard와 일반적인 recoverable commit을 허용합니다. Inventory membership은 entitlement evidence가 아니며 verification rejection은 inventory availability와 구분합니다. Manual binding 밖의 exact Kimi ModelTarget은 최초 범위에서 authenticated snapshot을 우회하지 않습니다. 따라서 non-interactive Kimi connect는 authored replay profile 자체가 durable plaintext-retention acknowledgment인 explicit manual binding이 필요하고, catalog onboarding은 controlling-TTY two-part flow로 유지합니다.

Non-interactive external connect는 정확한 ModelTarget 하나와 `--credential-file PATH`, `--yes`를 요구합니다. 두 옵션은 항상 함께 사용하고 Local Codex 및 두 부분 discovery target에서는 거절합니다. Discovery는 non-interactive mode에서 model을 추측하지 않습니다. `--yes`는 이미 캡처한 unambiguous plan, 정확한 ConfigSnapshot, CredentialRevision, ConnectionRevision만 승인하므로 target 범위를 넓히지 않고 confirmation만 생략합니다. Command는 pending recovery를 해결하고 plan을 준비한 다음 credential-store 계약을 통해 credential file을 열고, interactive connect와 같은 one-attempt complete binding-union verification, 마지막 ConfigSnapshot guard, journal publication, commit을 수행합니다. Credential-file 캡처 또는 verification 실패는 새로 계획한 connect의 intent나 repository mutation을 만들지 않고 TTY나 다른 secret source로 fallback하지 않으며 source file을 그대로 둡니다. Plan 이전의 mandatory recovery는 기존 journaled operation을 이미 완료했을 수 있고, 이 earlier recovery는 새 connect의 failure guarantee에 포함하지 않습니다. 두 옵션이 모두 없으면 기존 controlling-TTY confirmation과 no-echo secret input을 그대로 사용합니다. `--verbose`는 interactive confirmation 전용이므로 non-interactive `--yes`와 함께 사용할 수 없습니다.

Interactive disconnect는 관리형 target 하나를 묻거나 추론합니다. Non-interactive disconnect는 정확한 Provider와 `--account`, `--yes`가 필요하고, `--yes`는 캡처한 plan과 revision만 승인합니다. 캡처한 ConfigSnapshot과 prospective managed snapshot에서 target Provider·Account pair의 post-public effective binding set을 계산합니다. 남는 수동 또는 관리형 외부 binding이 그 pair를 계속 요구하면 credential action은 `preserve`이고, post-public dependent가 없을 때만 prepared `remove`를 허용합니다. 따라서 같은 identity의 수동·관리 binding이 합쳐진 상태에서 관리 provenance만 제거하면 수동 binding과 credential은 계속 사용할 수 있습니다. Preview는 영향받는 binding, preference transition, resume risk, 계산된 credential action을 보여줍니다. 수동 전용 entry는 Yo가 제거할 수 없고 `config.yaml`을 수정하도록 안내합니다. Public removal과 preference transition을 credential removal보다 먼저 commit하며 public-first recovery table이 모든 exact crash state를 이어가거나 완료로 인식합니다. Durable history는 유지합니다.

하나의 operation lock이 connect, disconnect, first-success Local Codex preference 게시, explicit default 설정 또는 해제를 serialize합니다. 이 모든 command는 새 작업을 계획하기 전에 pending operation journal을 해결합니다. CredentialRevision은 credential store와 권한 제한 operation journal 안에서만 private하게 유지합니다. 사용자에게 보이는 typed conflict와 partial outcome은 operation kind, phase, 계산된 preserve/remove action, expected 또는 committed ConnectionRevision과 안전한 retry 안내만 표시하고 CredentialRevision이나 secret은 노출하지 않습니다. Retry는 idempotent하며 관련 없는 data를 복원하거나 삭제하지 않습니다. Tenant 선택과 UI, rotation policy, failover는 미루되, 주입 가능한 경계로 미래 caller-owned tenant scope를 보존하고 지금 TenantId를 추가하지 않습니다.

## 이유

명시적인 resolved field를 사용하면 두 번째 content-addressed identity를 만들지 않고도 설정을 읽기 쉽게 유지하고 equality 진단으로 어느 값이 다른지 설명할 수 있습니다. Command-local config reload는 일반적인 상용 도구 동작과 맞고, direct identity conflict는 두 source가 같은 좌표를 서로 다르게 routing하는 것을 막습니다. CandidateSecret 전용 검증은 credential-first 추가 또는 교체 중 기존 binding을 보호하고, operation별 복구표는 수동 또는 관리 provenance가 계속 요구하는 credential을 삭제하지 않으면서 public-first disconnect를 보존합니다. 단일 저장소 preference mutation에는 저장소 간 journal이 필요하지 않습니다. Prepared ConnectionRepository CAS 자체가 old public state 또는 exact new public state만 만들고, fresh retry가 잃어버린 in-memory verification이 durable authority가 되는 것을 막습니다.

Inventory와 현재 availability를 분리하면 remote model identity를 안정적으로 유지하면서 Yo runtime 지원을 확장할 수 있습니다. Capability metadata는 유효한 model을 숨기는 대신 effective behavior를 좁힙니다. Tool calling이 없는 text model은 `no-tools/v1`로 계속 사용할 수 있고, Yo가 아직 실행할 수 없는 modality는 정확한 reason과 함께 표시되며 해당 runtime capability를 구현하면 같은 model이 eligible해집니다.

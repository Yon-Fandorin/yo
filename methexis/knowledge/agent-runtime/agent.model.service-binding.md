# Model service binding and managed connections

## Statement

Routing uses typed stable ProviderId, AccountId, and ModelId. A new managed ProviderId `host` is forbidden; a pre-existing manual or durable `host` coordinate remains a qualified ModelTarget with stable credential, attribution, and continuation identity. Provider names the service group, Account the credential scope, and Model the wire model name. External keys are `provider`, `account`, and `model`. An exact Responses or Chat Completions dialect resolves through the closed registry to one Connector; probing and fallback are forbidden.

Model connection and profile values remain explicit typed data; this unit does not assign them a canonical byte encoding or durable profile digest. A Provider-and-Account binding declares exactly one normalized endpoint outside its profile and model entries cannot replace it. The binding may declare one base profile above its model entries. Each model entry may omit inherited fields or replace only a closed set of named profile fields: `api_dialect`, `tokenizer_profile`, `input_token_limit`, `max_output_tokens`, `reasoning_parameters`, `optional_request_parameters`, `tool_capability_policy`, `verification_profile`, and `replay_profile`. Resolution copies the base profile and then replaces each field explicitly present on the model; a structured field is replaced as a whole rather than recursively merged. Unknown or duplicate authored fields fail, as does a missing endpoint or any missing required profile field after resolution. Omitting a model profile field inherits the base value, while an explicitly authored empty mapping replaces a structured field with that empty mapping. An explicitly authored whole-field YAML null fails at both the manual-configuration and durable managed-state decode boundaries for every profile field; null remains part of the recursive structured-value algebra only below a present structured field. No implicit default supplies the endpoint or first eight profile fields; the exact replay-profile omission rule below is the sole semantic default.

The resolved effective profile contains the model's API dialect, tokenizer profile, input-token capability, maximum-output capability, reasoning parameters, optional request parameters, tool-capability policy, verification profile, and replay profile. Capability limits describe supported bounds; an actual per-request output limit remains a request parameter. Each profile identifier uses the exact `yo.versioned-profile-id/v1` grammar: 1 to 128 ASCII octets, a non-empty name matching `[a-z0-9][a-z0-9._-]*`, then `/v`, then `[1-9][0-9]*`. Input and output capabilities are positive and `max_output_tokens` is less than `input_token_limit`; runtime use separately requires implementation support.

`replay_profile` is explicit complete-binding and epoch identity. The first closed values are `semantic-only/v1` and `kimi-private-local-plaintext/v1`. `semantic-only/v1` declares exact provider-neutral replay and no provider-private schema. `kimi-private-local-plaintext/v1` declares exact replay schema `kimi.assistant-message/v1alpha1`, local-client execution, and unencrypted retention in the current-user-only Session Repository. For compatibility, an authored or durable binding that omits the field decodes as exact `semantic-only/v1` without rewriting its bytes; no ModelId, Connector, release overlay, or runtime default may reinterpret that omission as the private profile. Consequently an older K3 or K2.7 Code coordinate that lacks the private profile remains unsupported and quarantined after upgrade rather than being silently enabled. A manual K3 or K2.7 Code binding is eligible only when the operator explicitly authored `kimi-private-local-plaintext/v1`; a managed K3 or K2.7 Code binding receives that value only from the exact Kimi plan whose plaintext-retention disclosure the operator confirmed. The dynamic overlay may prepare such a candidate but MUST NOT itself turn an unconfirmed or older stored binding into durable authorization.

The current config and `connections.yaml` readers accept the exact preceding profile shape with absent `replay_profile` under that one mapping and accept the extended shape with one non-null versioned string; whole-field null, duplicate, unknown, and malformed values fail. The current managed producer canonically omits `semantic-only/v1` and emits exact `replay_profile: kimi-private-local-plaintext/v1` for every member of the closed current private-replay envelope: Platform endpoint `https://api.moonshot.ai/v1/` with exact `kimi-k3`, `kimi-k2.7-code`, or `kimi-k2.7-code-highspeed`; and Code endpoint `https://api.kimi.com/coding/v1/` with exact `k3`, `k3-256k`, `kimi-for-coding`, or `kimi-for-coding-highspeed`.

`config.yaml`, `connections.yaml`, `credentials.yaml`, and the connection-operation journal use one current pre-version YAML document shape and carry no top-level format-version field. The retired top-level `version` field and retired journal `profile_digests` field are unknown and fail before mutation. This is an intentional pre-release replacement: Yo provides no legacy decoder, automatic migration, dual write, downgrade shim, or automatic deletion. When preceding local bytes are encountered, Yo reports that the operator must back up or remove the stale local state and register the connection again. A preceding operation journal is likewise unsupported rather than reinterpreted under the current parser.

Each reader for the four local model-service YAML documents named above uses the same shared safe-Rust parser boundary. It accepts exactly one document, permits aliases only within finite structural and replay bounds, and rejects unknown aliases, alias cycles, duplicate mapping keys, merge keys, additional documents, and configured event, node, depth, scalar-byte, anchor, alias, or replay-budget exhaustion. Exact numeric budget values are implementation limits rather than compatibility promises; they remain finite and tests pin each failure class.

`tool_capability_policy` is the closed durable maximum for request-local tool exposure rather than a claim that every request or remote model uses tools. The initial runtime accepts exactly `local-tools/v1` and `no-tools/v1`. Each Connector request separately carries a non-durable exposure mode of `enabled` with one frozen registry projection or `disabled`; this mode does not change complete binding identity or open an epoch. An ordinary Yo-managed agent request under `local-tools/v1` uses enabled exposure, while `no-tools/v1` forces disabled exposure and an empty runtime registry. Every bounded connection-verification request uses disabled exposure regardless of the binding policy. Enabled exposure is invalid under any policy other than `local-tools/v1`. Connector tool definitions and tool-selection fields follow this request-local exposure mode, not the durable policy alone.

A complete manual or managed binding retains its exact effective policy. For an OpenRouter discovery row with valid capability metadata, ordinary base-plus-model profile resolution happens first, including any authored whole-field model override. That row's resolved configured policy is the maximum the operator permits: resolved `no-tools/v1` remains `no-tools/v1`, while resolved `local-tools/v1` remains `local-tools/v1` only when `supported_parameters` contains both `tools` and `tool_choice` and otherwise narrows to `no-tools/v1`. Remote metadata never broadens a configured policy, and no other supported-parameter string rewrites a profile field in the initial scope.

The first activation of `no-tools/v1` is one compatibility transition. A Checkpoint MUST NOT select a service-binding revision that admits `no-tools/v1` unless that same forward Checkpoint selects Responses and Chat Completions revisions whose request contracts implement the request-local exposure rule above; those conditional Connector revisions likewise MUST NOT activate against a service-binding revision that lacks it. The activation request pins the three exact approved Knowledge revisions reviewed as one compatible set. Later revisions may replace a member only with a reviewed compatible revision while preserving the same complete active contract.

The first activation of the Kimi catalog, `kimi-chat-completions` dialect, and private replay profile is a second compatibility transition. Its forward Checkpoint MUST select the exact reviewed service-binding, Kimi Connector, Yo-managed model-loop, continuation-lineage, Session Repository, Session Journal, persistence-format, and session-selection revisions together. None may activate against older members of that set. The service revision MUST NOT activate without a Connector that implements its typed Kimi request and terminal grammar, the Connector and backend MUST NOT activate while the service registry cannot derive the exact dialect-and-Connector pair and replay profile, and no writer or selector may admit K3 before the semantic codec, physical repository, Anchor validation, visibility exclusions, and plaintext-retention authorization all implement the same private schema.

The first activation that admits `kimi-k2.7-code` or `kimi-k2.7-code-highspeed` is a third compatibility transition. Its forward Checkpoint MUST select the exact reviewed service-binding, Kimi Connector, Yo-managed model-loop, session-selection, continuation-lineage, Session Repository, and persistence-format revisions together. Those revisions reuse the existing `kimi.assistant-message/v1alpha1` semantic and physical storage shape; the compatible Session Journal revision need not advance. Neither the service, Connector, nor backend K2.7 Code revision may activate without the matching private-replay admission, consent, Anchor, storage, and wire-projection owners.

The first activation that admits the Kimi Code membership catalog is a fourth compatibility transition. Its forward Checkpoint MUST select the exact reviewed service-binding, Kimi Connector, Yo-managed backend, and session-selection revisions together. The backend supplies one provider-neutral per-Session cache-affinity hint without branching on Provider; only the revised Connector serializes it for the exact Code endpoint. The already active continuation, repository, Journal, and persistence-format revisions remain compatible because they admit provider-private replay by exact complete binding and replay profile rather than by one Platform ModelId. The Code membership service revision MUST NOT activate without a Connector that admits the exact `.com/coding/v1` endpoint and Code ModelIds, the backend cache-affinity owner, and selection enforcing the same plaintext-retention authorization for every private-replay Code binding.

Structured profile fields use a closed recursive value algebra of null, boolean, string, negative `i64`, nonnegative `u64`, finite `f64`, sequence, and mapping with unique string keys. Plain untagged scalar inference follows one shared order: an empty plain scalar, exact `~`, or case-insensitive `null` becomes null; case-insensitive YAML 1.1 boolean spellings `y`, `yes`, `true`, and `on` become true; `n`, `no`, `false`, and `off` become false; a negative integer representable as `i64` becomes signed; a nonnegative integer representable as `u64` becomes unsigned; a remaining finite numeral accepted by the shared YAML float grammar becomes `f64`; and every other scalar remains a string. Integer digit separators are accepted only between digits, so plain `1_000` is numeric `1000`. Quoted scalars and explicit string tags remain strings. Non-finite inferred numbers are rejected. Durable encoding preserves the resulting variants by emitting integers as integers and each `f64` with a float spelling. Float construction and decoding normalize `-0.0` to `0.0`. Equality is variant-exact and recursive: mapping key order is irrelevant, sequence order is significant, and integer `1` differs from float `1.0`. Decoding rejects duplicate mapping keys, non-string mapping keys, non-finite numbers, and values outside this algebra before comparison. No RFC 8785 serialization, SHA-256 profile identity, mutable profile registry, or recursive merge participates in equality.

The endpoint remains explicit connection data and uses `yo.normalized-model-endpoint/v1`, which freezes the exact parser and serializer behavior of Rust `url` crate version 2.5.8. It requires an absolute HTTPS URL with a host, rejects user information, query, and fragment, removes every trailing U+002F from the parsed path string, substitutes one U+002F when that result is empty, sets that path through the same serializer, and uses the resulting `Url::as_str()` ASCII value. `api_dialect` is exactly `openai-responses`, `openai-chat-completions`, or `kimi-chat-completions`; the corresponding Connector is derived through the closed registry, is not separately authored, and a mismatch fails.

Complete binding equality compares Provider, Account, Model, normalized endpoint, derived Connector, and every resolved effective-profile field directly. Any difference in the normalized endpoint, derived Connector, or resolved effective profile opens a new binding epoch. Durable attribution records an exact lossless typed snapshot of every complete-binding field rather than a profile digest. Display names and secrets are excluded.

Operator `config.yaml` is read-only and is never rewritten or pinned into ConnectionRepository. Every startup and command captures a fresh command-local ConfigSnapshot by opening the selected file once with no-follow semantics, requiring a regular file no larger than 1,048,576 bytes, performing a bounded read on that handle, and rejecting identity, size, or relevant metadata change during capture. An absent file is an ordinary empty manual snapshot. The exact captured bytes and their lowercase `sha256:` digest identify only that invocation; the next invocation always reads again.

ConfigSnapshot entries and managed entries first resolve their base profile plus model override, then compose by direct complete-binding equality. Equal bindings coalesce while retaining both provenances; manual display wins presentation, otherwise managed display is used. Unequal explicit values at the same Provider-and-Account-and-Model coordinate are `BindingConflict` and neither entry routes. The diagnostic shows both sources and exact non-secret field differences; resolution is to edit `config.yaml` or remove the managed binding with `yo disconnect`. The initial scope has no `reconcile` command and never silently chooses one source.

Before publishing a write-ahead intent or committing any managed repository mutation, including a preference-only mutation, the command captures `config.yaml` again and requires the same command-local digest and file identity. A difference aborts with `ConfigChangedRetry` before a credential or public commit. A manual edit racing after that guard does not retroactively change the captured in-flight plan; the operation completes or recovers against its exact prepared managed bytes, and the next invocation reloads the new file and either composes it or reports `BindingConflict`. Manual configuration is outside the managed operation lock, so the contract does not claim to serialize arbitrary editor writes.

ConnectionRepository, initially `connections.yaml`, owns managed bindings and accounts plus the selection-owned preference. It prepares a prospective bounded snapshot without changing bytes, reserves an independently generated planned ConnectionRevision, and binds its exact expected revision, planned revision, bytes, and selection transition into one immutable public mutation. Public CAS accepts only the expected or exact planned revision; observing the planned revision with exact intended bytes is idempotent success and every other winner conflicts.

Preference-only mutations are the first successful Local Codex HostTarget publication while the preference is unset, `yo default TARGET`, and `yo default --unset`. Under the same operation lock as connect and disconnect, the command first resolves any recoverable pending operation journal, then captures the exact PolicySnapshot, ConfigSnapshot, ConnectionRevision, bounded public bytes, and selection transition. After any required target-specific verification or admission and the final ConfigSnapshot guard, it commits exactly one ConnectionRepository CAS. Because no credential repository changes, a preference-only mutation MUST NOT publish an operation journal or name a CredentialRevision or credential action. The atomic old-or-new ConnectionRepository CAS is its durable recovery owner.

Interruption before that public CAS leaves the expected repository state; a later invocation captures fresh snapshots and repeats any required verification and admission instead of resuming lost in-memory evidence. Interruption after that CAS leaves the exact planned public state fully committed even when the caller did not observe success, so the caller must inspect the current preference. A later invocation is new authorization: when the requested explicit-default outcome already matches, it succeeds without mutation; otherwise `yo default TARGET` or `yo default --unset` may replace the current preference through a new CAS from its freshly captured revision. A later Local Codex connect can publish only when its fresh capture remains unset and therefore preserves any current winner. Public CAS protects concurrent changes between one invocation's capture and commit; it does not identify or preserve a winner across separate invocations. No path persists, reconstructs, or trusts lost verification evidence.

A credential-adding or credential-replacing `yo connect` is one recoverable serialized operation. Under the operation lock it captures the exact CredentialRevision, ConnectionRevision, ConfigSnapshot digest, old effective bindings, prospective managed snapshot, and selection transition. The newly disclosed secret remains an opaque in-memory CandidateSecret and is injected into every bounded no-tool verification request for every captured old binding that can remain effective before public commit and every prospective retained binding of that exact Provider-and-Account pair. Verification must not resolve or fall back to the currently stored secret. Its in-memory completion evidence binds the CandidateSecret handle, the complete verified identity set, and the exact prepared credential `add` or `replace`; only that complete evidence and the final ConfigSnapshot guard permit mutation. If any required old identity rejects the CandidateSecret, replacement fails and directs the user to remove or edit that binding before retrying.

Before the first repository commit of a credential-and-public multi-repository connect or disconnect operation, the orchestrator durably publishes a bounded current-user-owned mode-`0600` no-follow operation journal. It records a closed operation kind of `connect_credential_change` or `disconnect`; operation identity; ConfigSnapshot digest; exact expected and planned ConnectionRevision and prospective non-secret public bytes or their durable content-addressed artifact; phase; and one closed credential action. The pre-version document records no format-version or retired `profile_digests` field. `add`, `replace`, or `remove` records exact expected and planned CredentialRevision plus that exact pair intent, while `preserve` records only the exact expected CredentialRevision. The journal never contains a secret, CandidateSecret identity, or verification payload. Journal replacement is durable and atomic, and no repository commit is allowed before phase `intent` is durable. Preference-only mutations are excluded from this journal because their single public CAS has no cross-repository partial state to recover.

Recovery uses the journal's operation kind and credential action under the same operation lock. For `connect_credential_change`, the journal action must be exactly `add` or `replace`; credential CAS commits that exact prepared pair intent first, followed by durable phase `credential_committed`, public CAS, durable `public_committed`, then `complete`. Its exact state table is: expected credential plus expected public abandons the uncommitted intent and retry obtains the secret again; planned credential plus expected public commits the prepared public mutation; planned credential plus planned exact public bytes completes; every other state conflicts. For `disconnect`, public CAS commits first and phase `public_committed` becomes durable. With credential action `remove`, expected credential plus planned exact public commits the prepared credential removal, then `credential_removed` and `complete`; planned credential plus planned exact public completes. With `preserve`, expected credential plus planned exact public completes without credential mutation. Expected credential plus expected public abandons either disconnect intent, while planned credential plus expected public and every unlisted state conflict. A journal phase may lag the repository state and advance only after the exact table comparison, but a phase that claims a commit not present in the repositories is a conflict rather than abandonment. Recovery never infers ownership from arbitrary revision change, restores a secret, invents a revision, or overwrites unrelated state; exact retry is idempotent.

An absent ConnectionRepository path is a canonical empty managed snapshot with revision token `absent` and no bindings or preference. Its first writer creates an exclusive same-directory current-user-owned no-follow temporary with mode `0600`, durably writes the prepared snapshot, and atomically renames only if the expected repository revision remains absent. A concurrent winner causes re-read and exact-intent reuse or conflict. Existing writes use bounded regular snapshots, prepared opaque revision CAS, durable atomic replace, old-or-new recovery, and unrelated preservation. An injected repository must provide equivalent semantics.

OpenRouter, QwenCloud, and Kimi remain configured Providers. A base profile may remove repetition across manual model entries, while a model override keeps exceptional values next to that model. Stored snapshots keep these values explicit and readable; custom profiles remain an advanced path. OpenRouter and Kimi each own a distinct authenticated account-model inventory protocol described here; neither protocol becomes a generic Model Connector responsibility and neither may decode the other Provider's wire fields.

An OpenRouter Provider-and-Account binding may omit model entries only when it supplies the exact OpenRouter ProviderId, one normalized endpoint, and a complete base profile. Such a binding is a discovery seed rather than a routable ModelTarget. Interactive two-part target admission is closed: `yo connect Provider:Account` accepts only an exact configured OpenRouter discovery seed, an exact configured QwenCloud catalog seed, or an exact configured Kimi catalog seed and rejects every other two-part target. Only the OpenRouter seed performs the authenticated remote discovery in this paragraph; QwenCloud and Kimi follow their separate catalog flows below. The OpenRouter command appends path segments `models` and `user` to the normalized endpoint without replacing an existing path prefix and performs one authenticated same-origin `GET`. It sends the in-memory CandidateSecret only as a Bearer credential, never forwards it across an origin change, permits at most three same-origin redirects, uses a 10-second connection timeout, a 30-second response-header timeout freshly started for every dispatched attempt, a 30-second response-body inactivity timeout reset by each non-empty chunk, and a two-minute absolute deadline. A success response must have a JSON media type and fit within 8,388,608 bytes. Its `data` array must contain no more than 4,096 rows; 4,097 or more rejects the whole response before row admission rather than truncating or choosing a subset. Transport, status, media-type, size, and decode diagnostics expose neither the credential nor response-body content. There is no background refresh, disk cache, or automatic retry in this scope.

The discovery response must contain a `data` array. Inventory membership and current runtime availability are separate. A non-object row or a row without a string `id` is omitted because it has no representable identity. The row uses `id`, not `canonical_slug`, as the durable ModelId, and an invalid ModelId is omitted. After that identity validation, the first row for an exact ModelId wins even when it is disabled and every duplicate is ignored; no other capability, limit, or profile condition removes that row from the in-memory inventory. `architecture.input_modalities`, `architecture.output_modalities`, and `supported_parameters` are capability evidence. Each must be an array containing only strings; valid arrays are interpreted as duplicate-free, order-insensitive sets while unknown strings remain bounded untrusted in-memory metadata. Missing or malformed capability evidence disables the row as `capabilities unavailable` rather than hiding it.

The initial runtime capability set accepts requests when both capability sets contain `text`; enabled rows are invoked only through Yo's text input and text output boundary, so additional advertised modalities do not disable a model that also supports text. A valid row lacking text input is disabled as `text input unsupported`, and one with text input but without text output is disabled as `text output unsupported`. Absence of `tools` or `tool_choice` does not disable a text model: its effective tool policy is derived as `no-tools/v1` under the configured-policy intersection above. A configured tool policy outside the two initially supported values disables the row as `tool policy unsupported`. The optional `reasoning` parameter affects only a presentation badge and does not invent reasoning parameters. Availability and its reason are derived runtime facts, not part of ModelId or durable provider identity; a later reviewed expansion of runtime modalities or policies re-evaluates the same exact ModelId without a provider-specific allowlist or connection migration.

A missing or JSON-null optional remote limit retains the configured limit value. A present `context_length` or `top_provider.max_completion_tokens` that is not a positive integer disables the row rather than hiding it, and a non-null `top_provider` that is not an object does the same. For a model already declared by the same configured binding, its authored whole-field overrides remain authoritative. Otherwise remote `context_length` replaces the base `input_token_limit` and remote `top_provider.max_completion_tokens` replaces the base `max_output_tokens` when present. Endpoint, dialect, tokenizer, structured parameters, and verification profile remain the explicit configured base values, while tool policy follows the capability intersection above. A row whose resulting complete profile is invalid is disabled as `profile unavailable`. When multiple conditions fail, the primary concise reason uses this order: unavailable capability evidence, unsupported text input, unsupported text output, unsupported tool policy, then unavailable profile. The normalized in-memory inventory is sorted by case-folded display label and then exact ModelId. An enabled selection retains that exact normalized row without a second fetch or invented metadata.

Every remote-derived string is untrusted terminal data. The picker and the later preview never write it raw: bytes outside ASCII U+0020 through U+007E and the ASCII quote and backslash bytes use a reversible visible escape, so C0/C1 controls, ESC/OSC payloads, line separators, bidirectional controls, and non-ASCII bytes cannot affect terminal state. A remote `name` is used only when its trimmed UTF-8 value is non-empty and no longer than 96 bytes; otherwise display falls back to the escaped ModelId. Each picker result occupies one terminal row and is clipped with a visible ellipsis to the measured terminal width, while the selected detail and later preview wrap the complete escaped ModelId without omission. Search compares the original ModelId and accepted original display name, but query rendering uses the same safe boundary. These rules affect presentation only; the exact unescaped ModelId remains the request and durable identity.

When the normalized inventory contains no valid ModelId, discovery fails before entering picker terminal mode. Otherwise the controlling-TTY picker opens even when every row is currently disabled, shows the Provider and Account once, and supports local case-insensitive substring search over display name and ModelId. Every matching inventory item remains reachable through a viewport of at most eight visible result rows. The first match is initially focused; Up and Down move focus by one result and clamp at the first and last result without wrapping, and the viewport scrolls just enough to keep the focus visible. Any edit to the search query recomputes the complete match set and focuses its first result. A query with no matches leaves the picker active with no focus so the operator can edit the query; Enter then does nothing. Enter on an enabled row accepts it. Enter on a disabled row keeps the picker active and shows its concise availability reason; Escape or interrupt cancels. Each row identifies the Model and concise context, output, tool, reasoning, and availability facts; it does not repeat Provider, Account, or the complete profile. From the first terminal-mode mutation, one scope-owned cleanup boundary restores the prior terminal mode and removes the dynamic panel on every exit: selection, Escape, interrupt, render or input failure, panic unwind, and ordinary error. Cleanup precedes the selected exact ModelTarget entering the existing concise connection preview. Only `--verbose` expands that later preview to the complete resolved profile. Cancellation or disabled-row inspection before confirmation discards the CandidateSecret and creates no new journal, credential mutation, or public mutation.

Interactive `yo connect` for an external service still changes exactly one binding. An exact ModelTarget follows the existing configured-model path. The OpenRouter two-part discovery target acquires the operation lock, resolves pending recovery, captures ConfigSnapshot and repository state, resolves the exact configured discovery seed, reads one CandidateSecret, fetches one account-scoped inventory, and lets the operator select exactly one enabled Model before preparing the same exact connect plan. A disabled item cannot be selected and cannot create a plan, journal, credential mutation, or public mutation. Discovery does not infer all models or a profile default. The same Provider-and-Account pair rotates or adds its secret. The later preview discloses the exact binding union and usage, confirms once, and verification makes no retry. The same CandidateSecret used for discovery is then verified against every required retained and prospective complete binding; final ConfigSnapshot validation, secret-free journal publication, credential-first commit, public commit, and recovery semantics remain unchanged. A selected `no-tools/v1` binding is verified through the same bounded no-tool path and later runs with an empty tool registry, while `local-tools/v1` behavior remains unchanged. Success proves authentication, exact entitlement, endpoint and dialect acceptance, and a semantic terminal result under finite bounds; failures remain distinct. The session-selection contract supplies any first-success preference transition, and the same public CAS publishes it with the binding.

A configured binding may select one built-in catalog adapter profile instead of authoring an endpoint, base profile, and model entries. `catalog` uses the exact `yo.versioned-profile-id/v1` grammar and is resolved through one closed in-process registry. Every adapter atomically owns its exact ProviderId, provider display fallback, normalized endpoint, inventory mode, and the typed profile data needed to turn one admitted row into a complete binding. A release-owned static adapter also owns bounded model membership and closed whole-field per-model replacements. An authenticated dynamic adapter instead owns its exact inventory request and decoder plus a closed release-owned behavior overlay; remote membership or metadata may fill only fields explicitly assigned to that decoder and cannot invent executable behavior. The binding still authors one AccountId and may author account or provider display labels, but `base_url`, `profile`, and `models` MUST be absent when `catalog` is present. A provider mismatch, unknown catalog profile, invalid adapter row or overlay, duplicate ModelId after the adapter's defined duplicate rule, or simultaneous catalog and manual connection fields fails configuration. Without `catalog`, the existing explicit endpoint, base-profile, and model-entry rules remain unchanged.

The static catalog registry admits exactly `qwencloud-coding-plan-cn/v1`, `qwencloud-coding-plan-intl/v1`, and `qwencloud-token-plan-team-intl/v1`, all bound to ProviderId `qwencloud`. They own the normalized endpoints `https://coding.dashscope.aliyuncs.com/v1/`, `https://coding-intl.dashscope.aliyuncs.com/v1/`, and `https://token-plan.ap-southeast-1.maas.aliyuncs.com/compatible-mode/v1/`, respectively. Their complete base profiles and per-model replacements are repository-owned typed data derived from the corresponding official plan documentation. General pay-as-you-go, workspace-dedicated, or other QwenCloud endpoints do not infer a catalog from their URL and remain explicit manual bindings. A later static Provider or plan requires a reviewed closed-registry expansion rather than claiming generic discovery.

A catalog profile names stable adapter behavior and service or plan family, not a content-addressed inventory snapshot or entitlement set. Each release-owned static catalog carries one deterministic, network-independent table of no more than 4,096 unique rows. An authenticated dynamic catalog instead holds one bounded invocation-local snapshot and never persists, refreshes, or treats it as durable state. Updating a static table or dynamic behavior overlay under the same catalog profile requires official provider-source evidence and ordinary review but does not mutate configuration or durable state. A removed, absent, or changed candidate never deletes or rewrites an already stored complete managed binding; startup decodes its exact durable fields and classifies any now-unsupported binding as quarantined rather than routable. Selecting the same coordinate from a later table, snapshot, or overlay uses ordinary complete-binding equality, so a field difference is an explicit replacement epoch rather than an implicit migration. A valid current-shape operation journal's exact planned public bytes remain the recovery authority across catalog updates that retain this pre-version decoder: recovery completes that plan even when the current catalog would reject it as a new addition, then quarantines the recovered binding so it is decodable and removable but never selectable, verifiable, or routable. A journal from the retired YAML shape is rejected instead of entering this recovery rule.

Catalog membership means only that the model is a candidate in the current release-owned table or invocation-local authenticated snapshot. It MUST NOT be presented as proof that an Account or CandidateSecret is entitled to use the model. Static rows and dynamic metadata plus their release-owned overlay must together supply explicit typed text modalities, tool support, reasoning presentation evidence, limits, dialect, tokenizer, structured parameters, tool policy, and verification profile before a routable complete binding exists. A row with unsupported runtime capability or no complete overlay remains visible but disabled with a concise reason; no provider-specific allowlist hides a valid dynamic ModelId. Catalog strings pass through the same terminal-safe presentation boundary, and the picker keeps the existing search, viewport, cancellation, disabled-selection, and cleanup behavior. The reasoning label distinguishes remote metadata from the effective execution mode. A reviewed release-owned overlay MAY supply a stronger exact-model fact when optional remote metadata is missing, but an explicit contradictory remote value disables the row as `capability conflict`; without such an overlay, missing or malformed metadata remains unknown and cannot broaden behavior.

A catalog binding is an onboarding seed and does not expand every bundled row into the manual ModelCatalog or make it routable at startup. Interactive `yo connect qwencloud:Account` is admitted only for one exact configured QwenCloud catalog seed. Under the operation lock the command resolves pending recovery, captures ConfigSnapshot and repositories, resolves the fixed in-process catalog without a credential or network request, and lets the operator select one enabled row. ## Rationale

Explicit resolved fields make configuration readable and make equality diagnostics explain which value differs without introducing a second content-addressed identity. Command-local config reload matches ordinary commercial-tool behavior while direct identity conflicts prevent two sources from silently routing the same coordinate differently. CandidateSecret-only verification protects retained bindings during credential-first addition or replacement, and operation-specific recovery tables preserve public-first disconnect without deleting a credential still required by manual or managed provenance. A single-store preference mutation needs no cross-repository journal: the prepared ConnectionRepository CAS already yields only the old or exact new public state, while fresh retry prevents lost in-memory verification from becoming durable authority.


Separating inventory from current availability keeps remote model identity stable while allowing Yo's runtime support to grow. Capability metadata narrows effective behavior instead of hiding valid models: a text model without tool calling remains usable through `no-tools/v1`, whereas a modality Yo cannot yet execute remains visible with a precise reason and becomes eligible when that runtime capability is implemented.

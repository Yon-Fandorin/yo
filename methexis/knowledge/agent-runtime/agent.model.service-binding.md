# Model service binding and managed connections

## Statement

Routing uses typed stable ProviderId, AccountId, and ModelId. A new managed ProviderId `host` is forbidden; a pre-existing manual or durable `host` coordinate remains a qualified ModelTarget with stable credential, attribution, and continuation identity. Provider names the service group, Account the credential scope, and Model the wire model name. External keys are `provider`, `account`, and `model`. An exact Responses or Chat Completions dialect resolves through the closed registry to one Connector; probing and fallback are forbidden.

Model connection and profile values remain explicit typed data; this unit does not assign them a canonical byte encoding or durable profile digest. A Provider-and-Account binding declares exactly one normalized endpoint outside its profile and model entries cannot replace it. The binding may declare one base profile above its model entries. Each model entry may omit inherited fields or replace only a closed set of named profile fields: `api_dialect`, `tokenizer_profile`, `input_token_limit`, `max_output_tokens`, `reasoning_parameters`, `optional_request_parameters`, `tool_capability_policy`, and `verification_profile`. Resolution copies the base profile and then replaces each field explicitly present on the model; a structured field is replaced as a whole rather than recursively merged. Unknown or duplicate authored fields fail, as does a missing endpoint or any missing required profile field after resolution; no implicit default supplies either one.

The resolved effective profile contains the model's API dialect, tokenizer profile, input-token capability, maximum-output capability, reasoning parameters, optional request parameters, tool-capability policy, and verification profile. Capability limits describe supported bounds; an actual per-request output limit remains a request parameter. Each profile identifier uses the exact `yo.versioned-profile-id/v1` grammar: 1 to 128 ASCII octets, a non-empty name matching `[a-z0-9][a-z0-9._-]*`, then `/v`, then `[1-9][0-9]*`. Input and output capabilities are positive and `max_output_tokens` is less than `input_token_limit`; runtime use separately requires implementation support.

Structured profile fields use a closed recursive value algebra of null, boolean, string, negative `i64`, nonnegative `u64`, finite `f64`, sequence, and mapping with unique string keys. Authored and durable decoders use one deterministic numeric classification: an integral spelling below zero becomes `i64`, a nonnegative integral spelling becomes `u64`, and a decimal or exponent spelling becomes finite `f64`; positive `i64` is not a representable variant. Durable encoding preserves that classification by emitting negative and nonnegative integers as decimal integers and every `f64` with a decimal or exponent marker. Float construction and decoding normalize `-0.0` to `0.0`. Equality is variant-exact and recursive: mapping key order is irrelevant, sequence order is significant, and integer `1` differs from float `1.0`. Decoding rejects non-finite numbers, out-of-range numbers, duplicate mapping keys, non-string mapping keys, and values outside this algebra before comparison. No RFC 8785 serialization, SHA-256 profile identity, mutable profile registry, or recursive merge participates in equality.

The endpoint remains explicit connection data and uses `yo.normalized-model-endpoint/v1`, which freezes the exact parser and serializer behavior of Rust `url` crate version 2.5.8. It requires an absolute HTTPS URL with a host, rejects user information, query, and fragment, removes every trailing U+002F from the parsed path string, substitutes one U+002F when that result is empty, sets that path through the same serializer, and uses the resulting `Url::as_str()` ASCII value. `api_dialect` is exactly `openai-responses` or `openai-chat-completions`; the corresponding Connector is derived through the closed registry, is not separately authored, and a mismatch fails.

Complete binding equality compares Provider, Account, Model, normalized endpoint, derived Connector, and every resolved effective-profile field directly. Any difference in the normalized endpoint, derived Connector, or resolved effective profile opens a new binding epoch. Durable attribution records an exact lossless typed snapshot of every complete-binding field rather than a profile digest. Display names and secrets are excluded.

Operator `config.yaml` is read-only and is never rewritten or pinned into ConnectionRepository. Every startup and command captures a fresh command-local ConfigSnapshot by opening the selected file once with no-follow semantics, requiring a regular file no larger than 1,048,576 bytes, performing a bounded read on that handle, and rejecting identity, size, or relevant metadata change during capture. An absent file is an ordinary empty manual snapshot. The exact captured bytes and their lowercase `sha256:` digest identify only that invocation; the next invocation always reads again.

ConfigSnapshot entries and managed entries first resolve their base profile plus model override, then compose by direct complete-binding equality. Equal bindings coalesce while retaining both provenances; manual display wins presentation, otherwise managed display is used. Unequal explicit values at the same Provider-and-Account-and-Model coordinate are `BindingConflict` and neither entry routes. The diagnostic shows both sources and exact non-secret field differences; resolution is to edit `config.yaml` or remove the managed binding with `yo disconnect`. The initial scope has no `reconcile` command and never silently chooses one source.

Before publishing a write-ahead intent or committing any managed repository mutation, including a preference-only mutation, the command captures `config.yaml` again and requires the same command-local digest and file identity. A difference aborts with `ConfigChangedRetry` before a credential or public commit. A manual edit racing after that guard does not retroactively change the captured in-flight plan; the operation completes or recovers against its exact prepared managed bytes, and the next invocation reloads the new file and either composes it or reports `BindingConflict`. Manual configuration is outside the managed operation lock, so the contract does not claim to serialize arbitrary editor writes.

ConnectionRepository, initially `connections.yaml`, owns managed bindings and accounts plus the selection-owned preference. It prepares a prospective bounded snapshot without changing bytes, reserves an independently generated planned ConnectionRevision, and binds its exact expected revision, planned revision, bytes, and selection transition into one immutable public mutation. Public CAS accepts only the expected or exact planned revision; observing the planned revision with exact intended bytes is idempotent success and every other winner conflicts.

Preference-only mutations are the first successful Local Codex HostTarget publication while the preference is unset, `yo default TARGET`, and `yo default --unset`. Under the same operation lock as connect and disconnect, the command first resolves any recoverable pending operation journal, then captures the exact PolicySnapshot, ConfigSnapshot, ConnectionRevision, bounded public bytes, and selection transition. After any required target-specific verification or admission and the final ConfigSnapshot guard, it commits exactly one ConnectionRepository CAS. Because no credential repository changes, a preference-only mutation MUST NOT publish an operation journal or name a CredentialRevision or credential action. The atomic old-or-new ConnectionRepository CAS is its durable recovery owner.

Interruption before that public CAS leaves the expected repository state; a later invocation captures fresh snapshots and repeats any required verification and admission instead of resuming lost in-memory evidence. Interruption after that CAS leaves the exact planned public state fully committed even when the caller did not observe success, so the caller must inspect the current preference. A later invocation is new authorization: when the requested explicit-default outcome already matches, it succeeds without mutation; otherwise `yo default TARGET` or `yo default --unset` may replace the current preference through a new CAS from its freshly captured revision. A later Local Codex connect can publish only when its fresh capture remains unset and therefore preserves any current winner. Public CAS protects concurrent changes between one invocation's capture and commit; it does not identify or preserve a winner across separate invocations. No path persists, reconstructs, or trusts lost verification evidence.

A credential-adding or credential-replacing `yo connect` is one recoverable serialized operation. Under the operation lock it captures the exact CredentialRevision, ConnectionRevision, ConfigSnapshot digest, old effective bindings, prospective managed snapshot, and selection transition. The newly disclosed secret remains an opaque in-memory CandidateSecret and is injected into every bounded no-tool verification request for every captured old binding that can remain effective before public commit and every prospective retained binding of that exact Provider-and-Account pair. Verification must not resolve or fall back to the currently stored secret. Its in-memory completion evidence binds the CandidateSecret handle, the complete verified identity set, and the exact prepared credential `add` or `replace`; only that complete evidence and the final ConfigSnapshot guard permit mutation. If any required old identity rejects the CandidateSecret, replacement fails and directs the user to remove or edit that binding before retrying.

Before the first repository commit of a credential-and-public multi-repository connect or disconnect operation, the orchestrator durably publishes a bounded current-user-owned mode-`0600` no-follow operation journal. It records a closed operation kind of `connect_credential_change` or `disconnect`; operation identity; ConfigSnapshot digest; exact expected and planned ConnectionRevision and prospective non-secret public bytes or their durable content-addressed artifact; phase; and one closed credential action. The exact prospective public bytes already contain the explicit managed connection and profile values, so new wire-v1 entries retain the required `profile_digests` field but emit it as an empty list. The wire-v1 decoder continues to require and validate that field, accepts pre-existing valid non-empty lists, and ignores their values for recovery. Thus existing pending wire-v1 journals remain recoverable without reinterpreting that published version. `add`, `replace`, or `remove` records exact expected and planned CredentialRevision plus that exact pair intent, while `preserve` records only the exact expected CredentialRevision. The journal never contains a secret, CandidateSecret identity, or verification payload. Journal replacement is durable and atomic, and no repository commit is allowed before phase `intent` is durable. Preference-only mutations are excluded from this journal because their single public CAS has no cross-repository partial state to recover.

Recovery uses the journal's operation kind and credential action under the same operation lock. For `connect_credential_change`, the journal action must be exactly `add` or `replace`; credential CAS commits that exact prepared pair intent first, followed by durable phase `credential_committed`, public CAS, durable `public_committed`, then `complete`. Its exact state table is: expected credential plus expected public abandons the uncommitted intent and retry obtains the secret again; planned credential plus expected public commits the prepared public mutation; planned credential plus planned exact public bytes completes; every other state conflicts. For `disconnect`, public CAS commits first and phase `public_committed` becomes durable. With credential action `remove`, expected credential plus planned exact public commits the prepared credential removal, then `credential_removed` and `complete`; planned credential plus planned exact public completes. With `preserve`, expected credential plus planned exact public completes without credential mutation. Expected credential plus expected public abandons either disconnect intent, while planned credential plus expected public and every unlisted state conflict. A journal phase may lag the repository state and advance only after the exact table comparison, but a phase that claims a commit not present in the repositories is a conflict rather than abandonment. Recovery never infers ownership from arbitrary revision change, restores a secret, invents a revision, or overwrites unrelated state; exact retry is idempotent.

An absent ConnectionRepository path is a canonical empty managed snapshot with revision token `absent` and no bindings or preference. Its first writer creates an exclusive same-directory current-user-owned no-follow temporary with mode `0600`, durably writes the prepared snapshot, and atomically renames only if the expected repository revision remains absent. A concurrent winner causes re-read and exact-intent reuse or conflict. Existing writes use bounded regular snapshots, prepared opaque revision CAS, durable atomic replace, old-or-new recovery, and unrelated preservation. An injected repository must provide equivalent semantics.

OpenRouter and QwenCloud remain provider-neutral configured Providers. A base profile may remove repetition across their model entries, while a model override keeps exceptional values next to that model. Stored snapshots keep these values explicit and readable; custom profiles remain an advanced path.

Interactive `yo connect` for an external service prompts for an omitted Provider and exactly one Model; it does not infer all models or a profile default. One invocation changes one binding. AccountId defaults to `default` only when the captured effective Provider has zero manual and managed accounts. Otherwise omission requires interactive selection of an existing account or an explicit new ID, and adding a new account requires `--account`. The same exact pair rotates or adds its secret. Verification discloses the exact binding union and usage, confirms once, and makes no retry. Success proves authentication, exact entitlement, endpoint and dialect acceptance, and a semantic terminal result under finite bounds; failures remain distinct. The session-selection contract supplies any first-success preference transition, and the same public CAS publishes it with the binding.

Non-interactive external connect requires one exact ModelTarget plus `--credential-file PATH` and `--yes`; the two options are valid only together and are rejected for Local Codex. `--yes` authorizes only the already captured unambiguous plan, exact ConfigSnapshot, CredentialRevision, and ConnectionRevision, and therefore suppresses the confirmation rather than broadening the target. The command resolves pending recovery and prepares the plan before opening the credential file through the credential-store contract, then performs the same one-attempt complete binding-union verification, final ConfigSnapshot guard, journal publication, and commits as interactive connect. A credential-file capture failure or verification failure creates no intent or repository mutation for the newly planned connect, never falls back to TTY or another secret source, and leaves the source file untouched. Mandatory recovery before that plan may already have completed a pre-existing journaled operation; this earlier recovery is not part of the new connect failure guarantee. The existing controlling-TTY confirmation and no-echo secret input remain unchanged when both options are absent. `--verbose` belongs to the interactive confirmation and conflicts with non-interactive `--yes`.

Interactive disconnect prompts or infers exactly one managed target. Non-interactive disconnect requires exact Provider and `--account` plus `--yes`; `--yes` authorizes only the captured plan and revisions. From the captured ConfigSnapshot and prospective managed snapshot it derives the post-public effective binding set for the target Provider-and-Account pair. If any remaining manual or managed external binding still requires that pair, credential action is `preserve`; only an empty post-public dependent set permits prepared `remove`. Thus removing one provenance from an equal coalesced manual-and-managed binding leaves the manual binding and its credential usable. Preview includes affected bindings, preference transition, resume risk, and the derived credential action. Manual-only entries cannot be removed by Yo and instead direct the user to edit `config.yaml`. Public removal and preference transition commit before any credential removal, and the public-first recovery table resumes or recognizes every exact crash state. Durable history remains.

One operation lock serializes connect, disconnect, first-success Local Codex preference publication, and explicit default set or clear. Every one of those commands resolves a pending operation journal before planning new work. CredentialRevision remains private to the credential store and permission-restricted operation journal. User-visible typed conflicts and partial outcomes name the operation kind, phase, derived preserve-or-remove action, and only expected or committed ConnectionRevision plus safe retry guidance; they never expose CredentialRevision or secrets. Retries are idempotent and never restore or delete unrelated data. Tenant selection, tenant UI, rotation policy, and failover are deferred, while injected boundaries preserve future caller-owned tenant scope without adding TenantId now.

## Rationale

Explicit resolved fields make configuration readable and make equality diagnostics explain which value differs without introducing a second content-addressed identity. Command-local config reload matches ordinary commercial-tool behavior while direct identity conflicts prevent two sources from silently routing the same coordinate differently. CandidateSecret-only verification protects retained bindings during credential-first addition or replacement, and operation-specific recovery tables preserve public-first disconnect without deleting a credential still required by manual or managed provenance. A single-store preference mutation needs no cross-repository journal: the prepared ConnectionRepository CAS already yields only the old or exact new public state, while fresh retry prevents lost in-memory verification from becoming durable authority.
